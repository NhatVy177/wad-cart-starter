One file is one module
// src/cart.js
export function cartTotal(items, options) { ... }

// test/cart.test.js
import { cartTotal } from '../src/cart.js'
export makes a name visible outside the file; import pulls it in
Modern syntax (ESM) needs one line in package.json: "type": "module"
The file extension is required in the import path — '../src/cart.js', not '../src/cart'

The JavaScript you need today
const items = [{ price: 180000, qty: 2 }, { price: 45000, qty: 1 }]

const subtotal = items.reduce((sum, i) => sum + i.price * i.qty, 0)  // 405000

npm and package.json
{ "name": "cart", "type": "module",
  "scripts": { "test": "node --test" } }
package.json is the project's identity card: name, type, scripts, dependencies
npm run <name> runs a script; npm test is the one we will use all semester
node_modules/ is downloaded, never written by you, and never committed
Every package you add is code you are responsible for. Add few

What a test is
import { test } from 'node:test'
import assert from 'node:assert/strict'
import { cartTotal } from '../src/cart.js'

test('empty cart costs nothing', () => {
  assert.equal(cartTotal([], { vatRate: 0.08 }), 0)
})
A test is a small program that fails loudly when your code is wrong
Node runs it: npm test. Red first, then green — that order matters
No library to install: node:test ships with Node

Part 2: the loop
Plan → Implement → Validate, and where you stand in it

Plan: what a brief contains
What to build, in one sentence
The files it may touch — and the ones it must not
The contract: inputs, outputs, and what happens on bad input
How you will know it worked
What it must not invent: libraries, endpoints, database columns

Two briefs for the same task
Weak	Strong
Ask	"add search to the product page"	"add a ?q= filter to GET /api/products, case-insensitive, matching name only"
Scope	unstated	"touch routes/products.js and its test; do not touch the schema"
Done	"make it work"	"npm test green, including an empty-result case"
Result	a new dependency, a changed schema, 300 lines	20 lines you can read in a minute

Implement: keep the steps small
One concern per run: a route, a component, a migration — not all three
Read the diff before you run it, not after it breaks
If the reply is much longer than the question, stop and re-brief
A fresh start with a better brief beats arguing with a long conversation

Validate: what "done" means
It runs, tests pass, linter and type checker are clean
You read every line and can explain it
You tried the failure case, not only the happy path
The diff contains nothing you did not ask for
Anything that fails here is a rule you were missing

Five red flags when reading generated code
An API that does not exist — the signature looks right, the function does not
A package you never chose, added quietly to package.json
Error handling that swallows the error — catch {}, or a log and nothing else
A second copy of something already in the repo
A test that cannot fail — it asserts the mock, not your code
